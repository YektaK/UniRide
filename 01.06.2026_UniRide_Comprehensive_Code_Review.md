# UniRide Codebase — Comprehensive Engineering Review

> **Date:** 2026-06-01
> **Scope:** `optimizer_api/`, `uniride_core/`, `academic_benchmark/`
> **Methodology:** Static analysis of source files, cross-reference of duplication, schema and lifecycle review
> **Reviewer focus:** Code quality, architectural debt, bugs, refactoring opportunities

---

## 1. Executive Summary

UniRide is a hybrid Next.js + FastAPI vehicle-routing research platform that exposes ~20 CVRP/CVRPTW algorithms through a single HTTP API and runs academic TSPLIB/CVRPLIB benchmarks on them. The codebase exhibits a clear **dual quality profile**:

- **The pure-Python algorithmic core** (`uniride_core/algorithms/sota_common/`, `clustering_strategies/`, `split_decoder.py`, `cvrptw_decoder.py`) is **production-grade**: well-typed, ABC-structured, numerically defensive, literature-referenced. This is the part of the code that would survive an academic peer review.
- **The API and CLI surface** (`optimizer_api/`, `academic_benchmark/cli_engine.py`, `academic_benchmark/sota_engine.py`) carries **substantial engineering debt**: god functions, parallel registries, runtime imports in hot paths, two parallel benchmark execution paths, and a 4× duplication of the strategy optimization body across GA/GWO/HHO/PSO strategies.

**Top-level metrics (from the read of the codebase):**

| Layer                                     | Approx. LoC | Duplication Ratio                                         | Type-Coverage               | Test Coverage |
| ----------------------------------------- | ----------- | --------------------------------------------------------- | --------------------------- | ------------- |
| `uniride_core/algorithms/`                | ~5 000      | **Low** (good factoring)                                  | High (PEP 604 unions)       | Strong        |
| `optimizer_api/strategies/` (algorithmic) | ~3 000      | **High** (≈70% body repeated 4×)                          | Medium                      | Medium        |
| `optimizer_api/routers/`                  | ~900        | Medium                                                    | Low–Medium (Pydantic helps) | Thin          |
| `academic_benchmark/`                     | ~5 000      | **Very high** (3 near-identical runners, 2 `compute_gap`) | Low                         | Smoke-only    |

**Top 5 critical issues to fix first:**

1. **GA/GWO/HHO/PSO strategy bodies are 95% identical** — `hybrid_base_strategy.py` exists for exactly this deduplication but its `optimize()` is empty. Removing the duplication would eliminate ~600 lines of copy-paste and fix 4 places instead of 1 on any future change.
2. **Two parallel benchmark execution paths** in both `optimizer_api/routers/benchmark.py` and `academic_benchmark/cli_engine.py` (with their own thread-spawning, persistence, exception-swallowing). Daemon threads with no graceful cancellation.
3. **Schema-less `BenchmarkRunRequest`** (Pydantic model with `Dict[str, Any]` for `algorithms` and `settings`) → no API contract, runtime errors instead of validation errors.
4. **Runtime imports inside hot paths** in `routers/benchmark.py:_academic_param_spaces()` and `registry_setup.py` executors — first-request latency penalty and re-import cost on every call.
5. **Sync `def` optimization endpoints in FastAPI** — blocks the event loop on a CPU-bound algorithm that can run 10–120s.

## 2. Strengths

The codebase is **not** a typical research prototype. There is clear evidence of intentional engineering:

### 2.1 Strong algorithmic core (`uniride_core/algorithms/sota_common/`)

- All major ALNS components use **abstract base classes** with `ABC` + `@abstractmethod`. Adding a new destroy/repair/penalty strategy is type-checked at import time.
- Mathematical formulation appears in **docstrings** (e.g. `P(accept) = exp(-ΔE/T)` for `SimulatedAnnealing`), with literature references (Ropke & Pisinger 2006 for ALNS).
- **Numerical safety**: `try/except (OverflowError, ZeroDivisionError)` in all acceptance criteria with `prob = 0.0` fallback. Epsilon-aware comparisons (`delta < -1e-10`) avoid floating-point noise triggering bad moves.
- The `IteratedPenaltyManager` (3-phase relax→moderate→strict) is a textbook IPM implementation; phase transitions are observable and reproducible.
- `MultiLayerLS` and `DiversityController` use edge-based Shannon entropy — a sound and standard diversity metric for ALNS populations.

### 2.2 Engine factory pattern (`uniride_core/algorithms/engine_factory.py`, `registry.py`)

- A clean registry → factory chain that allows the API layer to dispatch by name string. Backward-compatible aliases (`"ga"` → `GASplitEngine`) are explicit.
- Engine subclassing follows a `BaseEngine` ABC with `optimize()` contract.

### 2.3 Pydantic v2 schema discipline (partial)

- `OptimizationRequest.normalize_legacy_payload` accepts old benchmark/smoke-test payloads — a thoughtful schema-migration pattern.
- `StudentNode.validate_coordinates` enforces lat/lng bounds — small detail but prevents entire classes of bad input.
- Pydantic v2 `model_validator(mode="before")` is used correctly for input transformation.

### 2.4 Test infrastructure

- A wide test suite exists across both layers (`tests/test_*.py`). Smoke tests cover import-time contract violations, which catches the most common regression in a registry-based system.

### 2.5 Domain separation

- `uniride_core/` is **FastAPI-free** and is imported by both the API and the academic benchmark — a clean separation that allows benchmarking to evolve independently of the web layer. This is the right architecture and is rare in research code.

### 2.6 Configuration

- `.env`-driven CORS, version stamping (`"3.1.0"`), explicit `BenchmarkConfig.to_json/from_json` — the system is **deployable**, not just runnable.

## 3. Architectural Patterns

### 3.1 Three-layer architecture

```
uniride_core/        ← pure algorithms, no I/O, no HTTP
optimizer_api/       ← HTTP surface, schema validation, lifecycle
academic_benchmark/  ← CLI/research surface, statistical analysis
```

This is correct and should be preserved.

### 3.2 Registry pattern (with caveats)

Both `optimizer_api/strategies/__init__.py` and `uniride_core/algorithms/registry.py` use registries. The pattern itself is sound — but the API layer runs **two parallel registries** (instances + factories) that hold the same data. See §4.2.

### 3.3 Strategy pattern for ALNS components

`DestroyOperator`, `RepairOperator`, `AcceptanceCriterion`, `PenaltyManager` are all `ABC` with concrete subclasses registered by name. The same pattern is used in the strategy layer (`BaseRoutingStrategy` → `GAStrategy`, `GWOStrategy`, …).

### 3.4 Process/thread pool for parallelism

`ProcessPoolExecutor` is used for parameter tuning (`cli_engine.py:_tune_parameters`) and matrix benchmarks (`3_run_benchmark.py`). This is the right primitive for CPU-bound work.

### 3.5 Result dataclass (`RunResult`)

`engine_core.py:8` defines a comprehensive `RunResult` dataclass covering cost, gap, routes, capacity/TW violations, problem/matrix metadata. This is the right shape for downstream statistical analysis.

### 3.6 Anti-patterns observed

| Anti-pattern                        | Locations                                                            | Risk                                        |
| ----------------------------------- | -------------------------------------------------------------------- | ------------------------------------------- |
| God function                        | `routers/optimization.py:optimize_route` (5 concerns)                | Hard to test, hard to evolve                |
| Daemon thread for long-running work | `routers/benchmark.py:_start_benchmark_impl`                         | No graceful shutdown, no cancellation       |
| Runtime imports in hot paths        | `routers/benchmark.py`, `registry_setup.py` executors                | First-request latency, import churn         |
| Singleton registry at import        | `strategies/__init__.py:79–117`                                      | Tightly coupled; can't override per request |
| Duck-typed problem shim             | `cli_engine.py:_Problem` inner class, `sota_engine.py:type("P", ())` | Loses type safety, fragile                  |
| Hardcoded TSPLIB path               | `os.path.dirname(os.path.dirname(__file__))` × 3                     | Breaks on refactor                          |

## 4. Code Quality Issues

### 4.1 Critical — Strategy duplication (THE single biggest issue)

**Location:** `optimizer_api/strategies/{ga,gwo,hho,pso}_strategy.py`

Side-by-side comparison confirmed:

| Aspect                                              | GA             | GWO            | HHO            | PSO             |
| --------------------------------------------------- | -------------- | -------------- | -------------- | --------------- |
| File lines                                          | 342            | 279            | ~280           | ~290            |
| `optimize()` body lines                             | 199–342 (~143) | 147–279 (~132) | ~150–231 (~80) | 181–289+ (~108) |
| Build coordinates from depot+students               | ✓              | ✓              | ✓              | ✓               |
| Build time_matrix dict-of-dicts                     | ✓              | ✓              | ✓              | ✓               |
| Define `_dist(loc1, loc2)` closure                  | ✓              | ✓              | ✓              | ✓               |
| Convert students to `student_dicts`                 | ✓              | ✓              | ✓              | ✓               |
| Instantiate `VehicleCalculator(...)`                | ✓              | ✓              | ✓              | ✓               |
| Define `route_optimizer(location_codes)`            | ✓              | ✓              | ✓              | ✓               |
| Build `routes` list with `RouteStep`/`VehicleRoute` | ✓              | ✓              | ✓              | ✓               |
| Return `OptimizationResponse`                       | ✓              | ✓              | ✓              | ✓               |

**Differences (all of them, exhaustive):**

1. `request.ga_config` vs `request.gwo_config` vs `request.hho_config` vs `request.pso_config` (config accessor)
2. Strategy name in `vehicle_id`: `(GA)`, `(GWO)`, `(HHO)`, `(PSO)`
3. TSP solver: `solve_ga_tsp` vs `solve_gwo_tsp` vs `solve_hho_tsp` vs `solve_pso_tsp`
4. Minor: GWO uses `hasattr(request, 'gwo_config')` (line 165) while GA uses `if request.ga_config:` (line 217) — pure inconsistency

**The `hybrid_base_strategy.py` class already exists for this exact deduplication** but its `optimize()` is empty (it only has `_build_distance_matrix` and `_nearest_neighbor_tour` helpers). The docstring even says "Subclasses must implement: ... optimize()" — confirming the duplication is **acknowledged** in the codebase.

**Impact:** ~600 lines of near-identical code. Any change to the route-building/response shape must be made in 4 places, and they have already drifted (`hasattr` vs truthy check).

### 4.2 High — Two parallel registries

`optimizer_api/strategies/__init__.py` maintains:

```python
STRATEGY_REGISTRY: Dict[str, BaseRoutingStrategy]  # instances
STRATEGY_FACTORIES: Dict[str, Type[BaseRoutingStrategy]]  # classes
```

Both hold the same data. Both are populated by the same import-time loop. The codebase has multiple places where it must choose between them.

**Additionally:**

- `pipeline_map` (line 430) is a third hardcoded mapping of strategy → pipeline type — must be kept in sync with the registry.
- `_OPTIONAL_META` dict in `get_strategy_info()` is a fourth source of truth for optional strategy metadata.
- Backward-compat aliases like `"ga": _ga_strategy` and `"ga-split": _ga_split_strategy` are a fifth dimension.

A single class-level decorator (e.g. `@register_strategy(name, pipeline, ...)`) would collapse all five into one.

### 4.3 High — `BenchmarkRunRequest` is schema-less

```python
class BenchmarkRunRequest(BaseModel):
    algorithms: Dict[str, Any]
    settings: Dict[str, Any]
    problems: List[Dict[str, Any]]
    parameters: Dict[str, Any] | None = None
```

**Result:** any typo in the API payload is discovered at runtime, not at validation time. A misnamed parameter, an out-of-range value, an unknown algorithm key — all surface as 500 errors with stack traces. The Pydantic model exists but does almost nothing.

This is a contract regression. The same `optimize` endpoint validates 200+ fields; the benchmark endpoint validates ~5.

### 4.4 High — God function in `optimization.py`

`optimize_route()` at `routers/optimization.py` mixes 5 concerns:

1. Algorithm dispatch (lines 39–45)
2. Time-window post-processing (lines 47–60)
3. `ResourceProfiler` for IE telemetry (lines 68–95)
4. Bottleneck detection (lines 84–95)
5. Time-shift suggestions

The function is 200+ lines and depends on a long chain of utility imports. It cannot be unit-tested without monkey-patching the entire chain. Splitting it into `dispatch → profile → post_process → analyze` would make it testable, mockable, and reusable.

### 4.5 High — Two parallel benchmark paths in `cli_engine.py`

Lines 1204 (`_run_benchmark_with_best`) and 1225 (`_run_benchmark_direct`) are two runners that:

- Share 90% of their logic
- Have different exception handling
- Have different output persistence calls
- Both use daemon threads

A single `run_benchmark(..., use_tuning_cache: bool)` would eliminate the duplication. The same pattern is repeated in `routers/benchmark.py` (`_start_benchmark_impl` vs `_start_matrix_native_benchmark_impl`).

### 4.6 High — Runtime imports in hot paths

**`routers/benchmark.py:_academic_param_spaces()`** does:

```python
from academic_benchmark.param_spaces import NUMBA_PARAM_SPACES, SOTA_PARAM_SPACES
```

on every call. This adds tens of milliseconds to a request that should be a constant-time dict lookup.

**`registry_setup.py`** uses `importlib.import_module(...)` inside executor factories to dispatch SOTA solvers. With 6 SOTA algorithms and N routing aliases, this is `6 * N` re-imports per benchmark run.

**Fix:** Hoist all `param_spaces` imports to module load. Replace `importlib.import_module` with a module-level dispatch table.

### 4.7 Medium — Dead code

| Location                                                   | Dead code                                                       | Why it matters                                                                                                                                              |
| ---------------------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `destroy_operators.py:118`                                 | `GreedyInsertion._is_tw_feasible` always returns `True`         | Comment admits it is "simplified" — but it is silently wrong, not a placeholder. If anyone re-enables TW checking here, it will silently pass any solution. |
| `repair_operators.py`                                      | Same `_is_tw_feasible` simplified check                         | Same risk.                                                                                                                                                  |
| `routers/benchmark.py:_start_matrix_native_benchmark_impl` | Re-implements result persistence (already in `BenchmarkRunner`) | Either the runner or the impl is now wrong; the tests may not catch it.                                                                                     |
| `_archived/kmeans_tsp.py`                                  | 1 archived file                                                 | Mostly fine, but no `ARCHIVED.md` explains what to resurrect.                                                                                               |

**Recommendation:** delete the `simplified` `_is_tw_feasible` entirely and add a `NotImplementedError` (or call the real CVRPTW decoder). Archived code should have a manifest.

### 4.8 Medium — `compute_gap` has two implementations

| Location                                   | Signature                                | Returns                           |
| ------------------------------------------ | ---------------------------------------- | --------------------------------- |
| `academic_benchmark/core/evaluation.py`    | `compute_gap(actual_cost, optimal_cost)` | `float`                           |
| `academic_benchmark/benchmark_utils.py:77` | `compute_gap(problem, cost, optimal)`    | `(float, str)` (gap_pct, gap_str) |
| `academic_benchmark/registry_setup.py:330` | (calls the 3-arg form)                   | —                                 |

Three different call sites, two implementations, one of which is type-incompatible with the third. **The 3-arg form is a clear winner** (it has the problem context for error reporting and the formatted string for output).

### 4.9 Medium — `validate_param_value` is defined twice

`benchmark_utils.py:588` and `benchmark_utils.py:908` — different arity, different behavior. The 4-arg one returns a more verbose error message.

This is a classic copy-paste regression. One of them should be removed.

### 4.10 Medium — Mixed time sources

In the same files:

- `time.time()` for "now" / "started at"
- `time.perf_counter()` for elapsed (correct choice)
- `datetime.now(timezone.utc)` for serialization

`time.time()` is wall-clock and **jumps on NTP correction** — never use it for elapsed time. The codebase uses `time.perf_counter()` for measurements but `time.time()` for session timestamps. Use a single helper.

### 4.11 Medium — `shell=True` in `orchestrate_batch.py`

```python
subprocess.run(cmd, shell=True, capture_output=True, text=True)
```

If any of the `cmd` arguments include user input (the orchestrator takes problem indexes and file paths), this is a **shell injection** vector. Pass arguments as a list with `shell=False`.

### 4.12 Medium — Hardcoded model IDs in `orchestrate_batch.py`

```python
"1,2,3",  # berlin52
"4,5,6",  # eil51
...
```

These will break the moment the underlying TSPLIB database is updated. The orchestrator should **query the DB** for model IDs by problem name, not hardcode them.

### 4.13 Low — Turkish-language strings throughout `academic_benchmark`

`UYARI`, `SECIM`, `BILGI`, `HATA`, `Hosgeldiniz` appear in interactive prompts and log messages. This is fine if the user base is Turkish-only, but blocks internationalization and prevents automated translation tooling. **Recommendation:** extract all user-facing strings to a `messages.py` (or `messages_en.py` / `messages_tr.py`) module.

### 4.14 Low — Interactive `input()` calls block automated testing

`select_worker_count`, `select_run_count`, `select_mode`, `edit_param_space`, `_edit_param_space_interactive`, `_param_db_menu` — all use `input()`. The CLI cannot be tested in CI without a TTY shim, and cannot be scripted.

**Recommendation:** factor all `input()` calls into a single `prompter.py` that can be monkey-patched in tests.

### 4.15 Low — Inconsistent schema validation cost

`OptimizationRequest._matrix_is_asymmetric` is O(n²) over the distance matrix at validation time. For a 1000-node problem this is 1M comparisons **per request**. The result is then used only in a debug field. Either move this to a `model_validator(mode="after")` that runs only when `DEBUG` is true, or cache it.

## 5. Bugs and Risks

### 5.1 BUG — `ShawRemoval.destroy` max_dist never updates on missing distances

**Location:** `uniride_core/algorithms/sota_common/destroy_operators.py:222–226`

```python
max_dist = 1.0
for node in remaining:
    d = dist.get(seed_node, {}).get(node, 0.0)
    if d > max_dist:
        max_dist = d
```

If the distance dict has any missing edges (returns `0.0`), `max_dist` stays at `1.0`, and the normalization `d / max_dist` collapses to `0.0` for everything. The result: all remaining nodes have similarity `0.0` to the seed, and the roulette-wheel selection becomes uniform — ShawRemoval degrades silently to RandomRemoval.

**Reproduction:** Use any `dist` dict with sparse edges (e.g. from a partial observation dataset).

**Fix:**

```python
max_dist = max(
    (dist.get(seed_node, {}).get(n, 0.0) for n in remaining),
    default=1.0,
) or 1.0
```

### 5.2 BUG — `convert_schedule_to_students` mutable default

**Location:** `optimizer_api/routers/utils.py:54`

```python
def convert_schedule_to_students(..., user_mapping: Dict[str, Dict] = None):
```

`None` is fine as a sentinel, but the **type hint** says `Dict[str, Dict]` (non-Optional). The actual default is `None`, so the type hint is wrong and any IDE will flag it. **Fix:** `user_mapping: Optional[Dict[str, Dict]] = None` and an explicit `if user_mapping is None: user_mapping = {}`.

### 5.3 BUG — `get_time_windows` silently swallows IndexError

**Location:** `optimizer_api/models/schemas.py:237`

```python
return parts[0] * 60 + parts[1]
```

If `parts` is empty or has one element, this raises `IndexError`. The validator probably wraps this in a `try/except` somewhere, but if it does not, a malformed `"HH:MM"` string crashes the whole request validation. **Fix:** raise a clear `ValueError` with a meaningful message.

### 5.4 RISK — Sync `def` optimization endpoint blocks the event loop

`/api/v1/optimize` and `/api/v1/compare` are declared with `def` (not `async def`). FastAPI will execute the blocking algorithm in the same thread as the event loop. Under load, every other endpoint (`/strategies`, `/health`) becomes unresponsive.

**Fix:** wrap with `await run_in_threadpool(...)` or move to a dedicated worker process (Celery, RQ, Dramatiq).

### 5.5 RISK — Daemon threads with no cancellation

`routers/benchmark.py:_start_benchmark_impl` spawns a daemon thread. If the FastAPI process is shut down, the thread is killed mid-execution, leaving:

- Half-written CSV files
- A `BenchmarkRun` row in `"running"` state forever (no recovery on restart)
- A potential partial state in the SQLite `param_db`

**Fix:** use `asyncio.create_task` with a proper `try/finally` cleanup, or move benchmark execution to a subprocess (with checkpoint files).

### 5.6 RISK — `run_benchmark_task` swallows all exceptions

```python
try:
    ...
except Exception:
    benchmark_state_manager.fail_run(...)
```

The exception type, message, and stack trace are **never logged** at error level. The state manager presumably writes a `last_error` field, but the server's logs are silent. If a benchmark silently fails 100×, the user sees "failed" with no diagnostic.

**Fix:** `except Exception as e: logger.exception("benchmark failed: %s", e); fail_run(...)`.

### 5.7 RISK — `_make_legacy_executor` re-reads the distance matrix from disk on every call

**Location:** `academic_benchmark/core/registry_setup.py:179`

Inside the executor factory closure, the function calls `get_distance_matrix(...)` for **every** call, even though the matrix is loaded once and re-used across all algorithms. This is a 10–100× I/O amplification.

**Fix:** pre-load the matrix once at task dispatch time and pass it as an argument.

### 5.8 RISK — TSPLIB DB path is computed via parent-of-parent

```python
os.path.dirname(os.path.dirname(__file__))
```

If the package is ever installed differently (zip, namespace package, symlink), this breaks. **Fix:** use `importlib.resources` or a single source-of-truth constant.

### 5.9 RISK — Side-effect import in `sota_engine.py`

```python
os.environ.setdefault("OMP_NUM_THREADS", "1")
os.environ.setdefault("MKL_NUM_THREADS", "1")
```

at module top-level. This means **importing** `sota_engine` mutates the process environment, which can leak into the calling process (e.g. a Jupyter notebook). **Fix:** guard with a function-level initialization in `main()` and document the side effect in the docstring.

## 6. Recommended Refactorings

The recommendations below are ordered by ROI (impact / effort). Each is concrete and testable.

### 6.1 [HIGH ROI] De-duplicate GA/GWO/HHO/PSO strategies

**Target:** `optimizer_api/strategies/{ga,gwo,hho,pso}_strategy.py`
**Effort:** 4–6 hours
**Impact:** Removes ~600 lines, fixes 4 places instead of 1 on any future change

**Plan:**

1. Hoist the entire `optimize()` body to `HybridSplitBaseStrategy.optimize()` parameterized by:
   - `_solve_tsp_func: Callable` (the TSP solver to call)
   - `_strategy_label: str` (the name to embed in `vehicle_id`)
   - `_config_attr: str` (the request attribute to read)
2. Each subclass becomes ~30 lines: declare the three parameters and the config dataclass.
3. Add a test that verifies all 4 strategies produce structurally identical responses for the same input.

**Sketch:**

```python
class HybridSplitBaseStrategy(BaseRoutingStrategy):
    _solve_tsp_func: Callable = NotImplemented
    _strategy_label: str = NotImplemented
    _config_attr: str = NotImplemented

    def optimize(self, request):
        config = getattr(request, self._config_attr, None)
        coordinates = self._build_coords(request)
        time_matrix = data_loader.get_submatrix(...)
        # ... full body, using self._solve_tsp_func and self._strategy_label ...

class GAStrategy(HybridSplitBaseStrategy):
    _solve_tsp_func = staticmethod(solve_ga_tsp)
    _strategy_label = "(GA)"
    _config_attr = "ga_config"
    ga_config: GAConfig = None  # kept on the class for type access
```

### 6.2 [HIGH ROI] Replace `BenchmarkRunRequest` schema with strict types

**Target:** `optimizer_api/models/schemas.py`
**Effort:** 2 hours
**Impact:** Catches API contract violations at request time, not runtime

**Plan:**

```python
class AlgorithmSetting(BaseModel):
    name: str
    runs: int = Field(1, ge=1, le=100)
    params: Optional[Dict[str, ParamValue]] = None

class ProblemEntry(BaseModel):
    name: str
    category: Literal["small", "medium", "large", "xlarge"]
    capacity: int = Field(ge=1)

class BenchmarkRunRequest(BaseModel):
    algorithms: List[AlgorithmSetting] = Field(min_length=1)
    problems: List[ProblemEntry] = Field(min_length=1)
    workers: int = Field(1, ge=1, le=os.cpu_count() * 2)
    runs_per_problem: int = Field(1, ge=1, le=30)
    mode: Literal["sequential", "parallel", "tune-then-run"] = "sequential"
```

### 6.3 [HIGH ROI] Unify the two registries

**Target:** `optimizer_api/strategies/__init__.py`
**Effort:** 3 hours
**Impact:** Single source of truth, easier to add new strategies

**Plan:** Decorator-based registration:

```python
class StrategyRegistry:
    _items: Dict[str, StrategyMeta] = {}

    @classmethod
    def register(cls, name, *, pipeline, label, optional=False, **meta):
        def deco(klass):
            cls._items[name] = StrategyMeta(
                name=name, klass=klass, pipeline=pipeline,
                label=label, optional=optional, **meta,
            )
            return klass
        return deco

@StrategyRegistry.register("ga", pipeline="hybrid", label="(GA)")
class GAStrategy(HybridSplitBaseStrategy):
    ...
```

### 6.4 [HIGH ROI] Wrap sync optimization endpoints in threadpool

**Target:** `optimizer_api/routers/optimization.py`
**Effort:** 30 minutes
**Impact:** Restores event-loop responsiveness under load

**Plan:**

```python
from fastapi.concurrency import run_in_threadpool

@router.post("/optimize")
async def optimize_endpoint(request: OptimizationRequest):
    return await run_in_threadpool(optimize_route, request)
```

### 6.5 [MEDIUM ROI] Hoist runtime imports to module load

**Target:** `routers/benchmark.py:_academic_param_spaces`, `registry_setup.py` executors
**Effort:** 1 hour
**Impact:** First-request latency drops, import churn eliminated

**Fix:** Move all `from … import …` statements to module top. Replace `importlib.import_module(...)` with a precomputed dispatch table.

### 6.6 [MEDIUM ROI] Consolidate benchmark execution paths

**Target:** `academic_benchmark/cli_engine.py:1204, 1225`, `optimizer_api/routers/benchmark.py:240, 433`
**Effort:** 4 hours
**Impact:** Single execution path, consistent error handling, testable

**Plan:** Create a `BenchmarkRunner` class with one `run(config: BenchmarkConfig) -> RunResult` method. The two CLI functions become thin wrappers passing different `BenchmarkConfig` values. The router path uses the same class with different persistence.

### 6.7 [MEDIUM ROI] Split `optimize_route` god function

**Target:** `optimizer_api/routers/optimization.py`
**Effort:** 2 hours
**Impact:** Testable, mockable, reusable

**Plan:** Extract into:

- `dispatch_algorithm(request) -> OptimizationResult` (the existing 50 lines)
- `apply_time_windows(result, request) -> OptimizationResult` (the post-processing)
- `profile_resources(result) -> ProfileReport` (the ResourceProfiler)

## 8. Final Verdict

**UniRide is a research-grade platform that is approaching production-grade.** The algorithmic core is well-engineered, the domain separation is clean, and the test infrastructure exists. The main issues are concentrated in the **API surface** and the **academic CLI**, where the duplication, god functions, and missing schema validation dominate the maintenance cost.

**To move from research-grade to production-grade, in order:**

1. **De-duplicate the four strategies** (4.1) — single largest win, removes ~600 lines.
2. **Tighten `BenchmarkRunRequest`** (4.3) — gives the API a real contract.
3. **Wrap sync endpoints in threadpool** (5.4) — restores event-loop responsiveness, no risk.
4. **Split the god function** (4.7) — unblocks unit testing.
5. **Unify the two benchmark paths** (4.5) — single execution surface.
6. **Fix the ShawRemoval bug** (5.1) — small, definitive, with a test.
7. **Hoist runtime imports** (4.6) — pure latency win.
8. **Add structured logging and exception handling** (5.6, 6.13) — observability.

After these 8 changes, the codebase will be in a state where:

- New algorithms are added in one place (parameterized base class)
- The API has a real contract (typed request models)
- The event loop is healthy (threadpool offload)
- The benchmark pipeline has one execution path
- Bugs in the core algorithm are caught by tests with sparse inputs
- Production issues are debuggable from logs alone

**Estimated total effort: 3–5 engineer-days.** High confidence on the de-duplication win; medium confidence on the timing of the others given the coupling between `routers/benchmark.py` and `academic_benchmark/cli_engine.py`.

The codebase is **not** "broken" — it is a real, runnable, partially-tested system. The recommendations above are about reducing technical debt to a level where the next 6 months of feature work are not blocked by the existing 6 months of accumulated shortcuts.
