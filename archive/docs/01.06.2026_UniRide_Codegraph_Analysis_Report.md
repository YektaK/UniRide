## 1. Executive Summary

Codegraph analysis of the UniRide codebase reveals a **well-structured strategy/registry pattern** with a clean three-layer architecture, but the index is **polluted by archive candidates** (`.proposed_changes/` snapshots) that inflate symbol counts and blur blast-radius analysis.

**Key structural findings:**

| Metric | Value | Notes |
|---|---|---|
| Total symbols indexed | ~2 000+ | Across 200+ files |
| `optimize()` runtime dispatch targets | **17** types | Strategy pattern — dispatch is dynamic, not static |
| ALNS operator hierarchy | 4 destroy + 3 repair + 3 acceptance | All extend proper ABCs |
| Algorithm registry entries | ~40+ | `AlgorithmRegistry._registry` populated at import time |
| Files in `.proposed_changes/` polluting index | **~150+** | Archive snapshots from March–April 2026 |
| Blast-radius warnings (no covering tests) | **~12** | Critical algorithms with no test coverage detected by codegraph |

**The single most important codegraph finding:** the `optimize` method on `BaseRoutingStrategy` is a **runtime dispatch point** — there is no single static caller→callee edge. The 17 implementations ARE the continuations. This is the correct strategy pattern, but it means static analysis tools (including codegraph) cannot trace a specific `/optimize` request to a specific algorithm without runtime information.

### 3.3 Registry pattern — two parallel registries

Codegraph confirms the dual-registry finding from the code review:

1. **`AlgorithmRegistry`** (`academic_benchmark/engine_core.py:76`) — classmethod-based, used by the academic benchmark pipeline. Has `register`, `get_executor`, `list_algorithms`, `register_param_space`, `register_warmup`. Populated at import time by `registry_setup.py`.

**VehicleCalculator.calculate** flow (verified by codegraph):
1. Convert students → `Point` objects
2. `estimate_vehicle_count(points)` → initial `num_vehicles`
3. Iterative loop (`max_attempts = min(len(students) - num_vehicles + 1, 15)`):
   - `cluster_students(points, num_vehicles)` → clusters
   - For each cluster: call `route_optimizer(location_codes)` if provided
   - Check `route_duration > max_tour_time` constraint
   - If valid: return immediately
   - If invalid: track best-effort, increment `num_vehicles`
4. Fallback: best-effort clustering, or 1-student-per-vehicle
