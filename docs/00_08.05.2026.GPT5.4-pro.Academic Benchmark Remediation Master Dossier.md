2. Executive Position

---------------------

### Overall assessment

The benchmark stack is viable and worth fixing. It is not a rewrite situation.

### What is wrong right now

The main problems are not that the solvers are all broken. The deeper issues are:

* reproducibility drift in resumed SOTA runs
* invalid analytics caused by mixed raw and aggregate output semantics
* dashboard ingestion gaps
* solver-semantic mismatches in a few important areas
* incomplete interruption persistence
* several runtime/performance issues that matter after correctness is restored

### Most important principle

Fix correctness and semantic trust first.  
Fix dashboards and data contracts second.  
Fix optimization and runtime efficiency third.

5. Implementation Order

-----------------------

Phase 1: Reproducibility integrity
----------------------------------

### Goals

* resumed runs behave deterministically
* interrupted runs persist usable state

### Work

1. Fix SOTA resume seed continuity.
2. Populate active-results buffers in both engines.
3. Add tests for resume continuation and interruption persistence.

### Success gate

* no partial-cache run reuses earlier run indices
* interruption produces non-empty interrupted CSV output
* metadata and persisted rows agree on completed work

* * *

Phase 2: Semantic truthfulness of solver behavior
-------------------------------------------------

### Goals

* public APIs do what they claim
* local search behavior matches intended search semantics

### Work

1. Verify nb_three_opt implementation.
2. If it is a stub, implement real behavior or deprecate it explicitly.
3. Restore bounded iterative convergence in MultiLayerLS.
4. Add tests for both changes.

### Success gate

* nb_three_opt is no longer semantically misleading
* MultiLayerLS can improve beyond one pass on a designed case
* solver-validity tests still pass

* * *

Phase 3: Data contract cleanup
------------------------------

### Goals

* raw-run outputs are separated from aggregate outputs
* dashboard-facing semantics are explicit

### Work

1. Define run-level CSV schema.
2. Define aggregate summary schema.
3. Update both engines to emit both cleanly.
4. Add result_type, engine, mode, run_index, and seed fields where appropriate.

### Success gate

* no file mixes per-run and aggregate semantics
* robustness views can be built from raw data only
* benchmark_summary remains straightforward

* * *

Phase 4: Dashboard repair
-------------------------

### Goals

* dashboard loads the correct files
* dashboard stops making invalid statistical claims

### Work

1. Discover nested tuning paths.
2. Load raw-run, summary, and tuning sources separately.
3. Restrict robustness charts to raw-run rows only.
4. Add diagnostics for loaded files and row counts.
5. Improve refresh-safe caching.
6. Reproduce LaTeX behavior with missing optimal values before treating it as a confirmed issue.

### Success gate

* SOTA tuning is visible
* box plots use only independent trials
* dashboard shows what sources were loaded
* stale-file confusion is reduced

* * *

Phase 5: Algorithm-quality corrections
--------------------------------------

### Goals

* solver metrics and search flow better match problem semantics

### Work

1. Normalize R2DMA resonance for cyclic tours.
2. Remove prefix bias from P-AOEA mutation.
3. Extend Numba-backed 3-opt and swap coverage in LS engine if kernels exist and are stable.

### Success gate

* rotated-tour invariance tests pass
* mutation-diversity tests pass
* full-intensity LS uses accelerated paths where expected

* * *

Phase 6: Loader parity and runtime efficiency
---------------------------------------------

### Goals

* cross-engine problem corpus stays aligned
* avoidable runtime overhead is reduced safely

### Work

1. Harmonize Numba loader behavior with SOTA.
2. Persist a loaded-problem manifest.
3. Review Numba cache policy.
4. Investigate repeated matrix rebuilds only if profiling justifies it.

### Success gate

* Numba and SOTA produce same normalized corpus under shared fixtures
* Numba cache policy is intentional and documented
* profiling-backed performance issues are addressed or explicitly deferred

9. Decision Rules

-----------------

Use these rules to avoid getting stuck:

### Rule 1

If a problem is confirmed and affects correctness or semantic trust, fix it before performance work.

### Rule 2

If an issue is only “likely,” verify it quickly before doing broad refactors.

### Rule 3

If an issue is only “investigate,” do not let it block P0 or P1 work.

### Rule 4

If a fix changes benchmark semantics, add tests before optimizing it.

### Rule 5

If a dashboard issue reflects bad upstream data contracts, fix the producers first.
