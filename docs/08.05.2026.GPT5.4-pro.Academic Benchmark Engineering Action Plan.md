Academic Benchmark Engineering Action Plan
==========================================

**Date:** 2026-05-08  
**Author:** GitHub Copilot  
**Audience:** Engineering and research maintainers  
**Scope:** Numba engine, SOTA engine, dashboard, solver semantics, test coverage, benchmark-result integrity, and verified follow-up performance issues

1. Goal

-------

Stabilize the academic benchmark stack so that benchmark runs are:

* reproducible after interruption or resume

* statistically valid across engines

* consistently ingestible by the dashboard

* defensible for academic comparison and publication use

* semantically faithful to the intended solver behaviors

* easier to maintain and extend
2. Immediate Problem Statement

------------------------------

The current benchmark system is broadly functional, but several implementation details reduce trust in end-to-end results:

1. Resume logic in master_sota_engine.py can reuse early seed indices instead of continuing missing run indices.

2. The dashboard currently mixes incompatible progress-row semantics from master_numba_engine.py and master_sota_engine.py, while describing them as raw multi-run observations in dashboard.py.

3. SOTA tuning output likely does not appear in the dashboard because master_sota_engine.py writes tuning results under a nested path not discovered by dashboard.py.

4. The R2DMA resonance metric in r2dma_tsp.py partly scores tours in a way that is sensitive to rotation, even though TSP tours are cyclic.

5. Numba problem loading in master_numba_engine.py is less robust than SOTA loading in master_sota_engine.py.

6. Interrupted-run buffer persistence appears incomplete in master_numba_engine.py and master_sota_engine.py.

7. A likely Numba semantic issue exists if the public nb_three_opt path still delegates to 2-opt behavior.

8. ls_engine.py currently behaves as a single-pass layered search rather than a repeated convergence loop.

9. 3-opt and swap appear not to use Numba acceleration in ls_engine.py.

10. The Numba cache strategy may be sacrificing runtime efficiency unnecessarily in local_search_numba.py.

11. Engineering Objective

------------------------

Move the benchmark system from “works in most cases” to “methodologically and operationally consistent.”

That means:

* every run has a stable run index and seed identity

* every output file has one clear semantic meaning

* every dashboard chart uses the correct data contract

* every engine loads the same effective problem corpus unless explicitly configured otherwise

* every solver metric respects the mathematical structure of TSP

* every public optimization API does what its name claims
4. Success Criteria

-------------------

The work should be considered complete only when all of the following are true:

1. Resumed SOTA runs continue missing run indices rather than restarting from zero.

2. Numba and SOTA both publish a shared run-level result format and a shared aggregate summary format.

3. The dashboard only uses run-level rows for variance and robustness views.

4. The dashboard discovers SOTA and Numba tuning outputs consistently.

5. R2DMA resonance treats cyclic equivalence in a principled way.

6. Numba and SOTA loaders produce the same problem-name set under the same local data conditions.

7. SIGINT recovery persists actual in-memory active rows, not only metadata.

8. nb_three_opt is either a true 3-opt path or explicitly renamed and documented otherwise.

9. MultiLayerLS supports iterative convergence semantics under a bounded runtime policy.

10. Regression tests exist for all of the above cases.

11. Workstreams

--------------

### Workstream A: Benchmark Data Contract Unification

Primary files:

* master_numba_engine.py
* master_sota_engine.py
* dashboard.py

Objective:  
Separate run-level observations from aggregate benchmark summaries.

Implementation direction:

1. Introduce a shared run-level CSV schema.
2. Keep benchmark_summary.csv aggregate-only.
3. Remove the assumption that benchmark_progress.csv is suitable for statistical plots.

Expected outcome:

* valid box plots
* clearer leaderboard logic
* cleaner cross-engine comparisons

### Workstream B: Resume and Cache Integrity

Primary file:

* master_sota_engine.py

Objective:  
Ensure resumed runs continue missing trial indices and preserve deterministic run identity.

Implementation direction:

1. Create new tasks with effective_run_idx = saved_runs + local_run_idx.
2. Use effective_run_idx for seed generation.
3. Store run_index explicitly in raw rows and metadata.

Expected outcome:

* deterministic continuation after resume
* no duplicate early trajectories
* defensible partial-resume experiments

### Workstream C: Dashboard Ingestion and Transparency

Primary file:

* dashboard.py

Objective:  
Make the dashboard consume the right files and expose what it loaded.

Implementation direction:

1. Discover tuning files recursively or via explicit known subpaths.
2. Add source labels such as engine, result_type, and file_origin.
3. Use run-level files only for robustness charts.
4. Display loaded file counts and warnings for missing sources.
5. Replace unconditional external-file caching with a refresh-friendly strategy.

Expected outcome:

* fewer silent omissions
* easier debugging of result visibility
* more trustworthy plots and exports

### Workstream D: Solver-Semantics Hardening

Primary files:

* r2dma_tsp.py
* paoea_tsp.py
* ls_engine.py
* bildiri2026

Objective:  
Improve algorithm behavior where semantics are currently weaker than they should be.

Implementation direction:

1. Canonicalize tours or redesign resonance terms in R2DMA to reduce rotation sensitivity.
2. Replace prefix-biased operator mutation in P-AOEA with true random-subset sampling.
3. Restore iterative convergence behavior in MultiLayerLS.
4. Implement or deprecate misleading nb_three_opt behavior.
5. Add larger-instance local-search pruning strategies or targeted heavy-search application.

Expected outcome:

* more principled solver behavior
* better search quality
* better agreement between public API names and actual behavior
* better scaling on medium and large instances

### Workstream E: Loader Parity and Resilience

Primary files:

* master_numba_engine.py
* master_sota_engine.py

Objective:  
Guarantee cross-engine corpus consistency under the same local data environment.

Implementation direction:

1. Make Numba use the same merge-and-deduplicate loader style as SOTA.
2. Use tolerant fallback file reading.
3. Persist a manifest of loaded problem names and sources.
4. Add a parity test between engines.

Expected outcome:

* same study corpus across engines
* fewer silent data discrepancies
* easier reproducibility audits

### Workstream F: Interrupted-Run Recovery Completion

Primary files:

* master_numba_engine.py
* master_sota_engine.py

Objective:  
Ensure interruption exports contain actual completed rows.

Implementation direction:

1. Append completed rows to the active-results buffer immediately after each successful result.
2. Keep metadata persistence as-is.
3. Validate that interrupted CSV output matches the number of completed tasks before exit.

Expected outcome:

* better crash resilience
* more credible long-run experiment handling
* reduced data-loss fear during manual interruption

### Workstream G: Numba Runtime Efficiency Review

Primary files:

* ls_engine.py
* local_search_numba.py

Objective:  
Recover avoidable runtime losses without compromising correctness.

Implementation direction:

1. Extend Numba-backed paths to cover 3-opt and swap where available.
2. Revisit the Numba cache policy and prefer per-process temp cache directories if safe.
3. Investigate repeated distance-matrix rebuilds in optimizer-side local-search wrappers.

Expected outcome:

* faster repeated runs

* more consistent benefit from JIT acceleration

* fewer avoidable CPU costs in hybrid local-search stacks
6. Recommended Implementation Order

-----------------------------------

### Phase 1: Integrity fixes first

1. Fix SOTA resume seed continuity.
2. Populate active-results buffers.
3. Add regression tests for resume and interruption behavior.

### Phase 2: Solver semantic truthfulness

1. Implement or deprecate misleading nb_three_opt behavior.
2. Restore iterative convergence semantics in MultiLayerLS.
3. Add tests for those behaviors.

### Phase 3: Data contract cleanup

1. Define run-level and aggregate output schemas.
2. Update both engines to emit consistent result files.
3. Keep legacy output temporarily only if migration support is needed.

### Phase 4: Dashboard repair

1. Update ingestion paths.
2. Separate chart sources by result type.
3. Add source diagnostics and refresh behavior.

### Phase 5: Algorithm-quality refinements

1. Normalize R2DMA resonance semantics.
2. Improve P-AOEA mutation diversity.
3. Add Numba acceleration coverage for 3-opt and swap.
4. Add local-search budget improvements for larger instances.

### Phase 6: Loader parity and runtime efficiency

1. Harmonize loader behavior.

2. Add corpus manifest output.

3. Add cross-engine parity tests.

4. Revisit Numba cache strategy.

5. Investigate repeated matrix rebuilds if still observed.

6. Validation Plan

------------------

### Validation A: Resume continuity

A partially cached SOTA run resumes only the missing trial indices.

### Validation B: Raw versus aggregate contract

The dashboard can load raw-run data and aggregate summary data without treating them interchangeably.

### Validation C: Tuning visibility

SOTA tuning output is visible in the dashboard without manual file relocation.

### Validation D: R2DMA cyclic equivalence

Resonance between equivalent rotated tours is materially closer to same-tour resonance than to unrelated-tour resonance.

### Validation E: Loader parity

Under the same local archive and fallback files, Numba and SOTA loaders produce the same normalized problem-name set.

### Validation F: SIGINT persistence

A simulated interrupted run produces both valid metadata and a non-empty interrupted CSV containing completed rows.

### Validation G: Numba semantic truthfulness

nb_three_opt no longer behaves identically to nb_two_opt by construction, unless explicitly deprecated.

### Validation H: MultiLayerLS convergence

A controlled test case demonstrates multi-pass improvement beyond the current single-pass outcome.

8. Risks

--------

### Risk 1: Output migration breaks downstream tools

Mitigation:

* keep a compatibility window or dual output during migration

### Risk 2: Dashboard assumptions are deeper than expected

Mitigation:

* add source metadata and explicit file-type labels early

### Risk 3: Solver semantic changes alter benchmark baselines

Mitigation:

* version-tag solver behavior changes and rerun baseline comparisons

### Risk 4: Numba cache changes reintroduce multiprocessing friction

Mitigation:

* test per-process temp cache directories before enabling persistent caching broadly
9. Definition of Done

---------------------

This action plan should be considered completed when:

1. Benchmark results are reproducible across resume scenarios.

2. Dashboard plots are driven by semantically correct inputs.

3. Tuning outputs are visible for both engines.

4. Loader parity is validated.

5. Solver-metric semantics are improved where mathematically necessary.

6. nb_three_opt is no longer semantically misleading.

7. MultiLayerLS convergence behavior is explicitly defined and tested.

8. Regression tests cover the failure modes identified in this review.

9. Final Recommendation

------------------------

Treat the current benchmark stack as structurally promising but not yet publication-safe. Prioritize reproducibility and semantic truthfulness first, then output contracts and dashboard correctness, then solver refinements and runtime optimization.
