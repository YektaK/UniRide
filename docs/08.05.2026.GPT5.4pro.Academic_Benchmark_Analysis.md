Academic Benchmark Review Report
================================

**Date:** 2026-05-08  
**Author:** GitHub Copilot  
**Scope:** Review of the academic_benchmark Numba engine, SOTA engine, supporting dashboard, shared benchmark utilities, related benchmark tests, and newly reconciled follow-up findings

1. Purpose

----------

This report reviews whether the academic benchmark programs are implemented correctly at a practical engineering level and identifies the most important correctness, reproducibility, UI, and algorithm-quality risks. It also provides solution advice for each problematic area so the benchmark stack can become more trustworthy for academic use.

4. Executive Summary

--------------------

### Overall assessment

The benchmark stack is directionally well-implemented and clearly more than a prototype. The core solver integrations, shared utility layer, and benchmarking structure show a consistent design.

In particular, the following are positive signals:

* Shared benchmark infrastructure is centralized in benchmark_utils.py.
* Solver-level tests exist and cover important baseline expectations in test_sota_e2e.py and test_sota_parity.py.
* Problem selection logic has dedicated tests in test_problem_selector.py.

### Bottom-line conclusion

The system is mostly implemented correctly at the solver and engine orchestration level, but it is not fully correct end-to-end for academic reporting, resumable benchmarking, or semantic consistency yet.

The most important risks are now:

1. Resume and cache behavior in the SOTA default engine can distort deterministic run continuity.

2. The dashboard mixes incompatible data semantics across Numba and SOTA progress files.

3. The dashboard likely misses SOTA tuning output entirely.

4. The R2DMA resonance metric is partly rotation-sensitive in a cyclic-tour problem.

5. The Numba loader is less robust than the SOTA loader and can benchmark a different effective corpus under degraded conditions.

6. A likely nb_three_opt semantic stub and the MultiLayerLS convergence-loop loss should be added to the engineering backlog.

7. Major Findings

-----------------

### 5.1 High Severity: SOTA cache-resume reuses early run seeds instead of continuing run indices

Relevant area:

* master_sota_engine.py

Problem:

When cached runs already exist, the engine reduces the number of remaining tasks correctly, but it still computes new seeds using run_idx starting from zero again. This means a resumed benchmark can regenerate seeds for runs that conceptually already exist, instead of continuing with the next missing run indices.

Why this matters:

* breaks deterministic resume semantics
* can duplicate earlier stochastic trajectories
* risks contaminating aggregated averages and variance reporting
* makes partially resumed academic runs less defensible

Solution advice:

1. Offset run_idx by saved_runs when generating resumed tasks.
2. Store the actual executed run index in result rows and metadata.
3. Add a regression test for partial-cache continuation.

* * *

### 5.2 High Severity: Dashboard robustness plots mix raw-run and aggregated benchmark rows

Relevant areas:

* dashboard.py
* master_numba_engine.py
* master_sota_engine.py

Problem:

The dashboard describes the robustness tab as using multi-run raw data, but the progress files do not mean the same thing across engines.

Why this matters:

* box plots can materially misrepresent variance
* Numba can appear artificially stable
* cross-engine academic comparisons become methodologically weak

Solution advice:

1. Split storage into explicit run-level and aggregate-level schemas.
2. Use only run-level rows for robustness charts.
3. Keep leaderboards and summary tables on aggregate outputs.

* * *

### 5.3 Medium Severity: Dashboard likely does not load SOTA DoE tuning output

Relevant areas:

* dashboard.py
* master_sota_engine.py

Problem:

The dashboard searches for tuning_progress.csv in a flat location while the SOTA engine writes tuning progress under a nested path.

Why this matters:

* the UI can silently omit completed tuning work
* comparative tuning analysis becomes incomplete

Solution advice:

1. Discover nested tuning directories such as engine-specific tuning folders.
2. Add a small loaded-source summary in the dashboard.

* * *

### 5.4 High Severity: R2DMA resonance metric is partly rotation-sensitive for cyclic TSP tours

Relevant area:

* r2dma_tsp.py

Problem:

Several resonance components compare tours using position-dependent order rather than cycle-equivalence-aware structure.

Why this matters:

* equivalent tours under rotation can be undervalued
* constructive versus destructive crossover decisions can be biased
* solution quality can degrade without an obvious crash or exception

Solution advice:

1. Canonicalize tours before resonance scoring.
2. Prefer cycle-structure features over raw positional alignment.
3. Add tests for rotation invariance and reversal handling.

* * *

### 5.5 Medium Severity: Numba TSPLIB loading is less robust and less consistent than SOTA loading

Relevant areas:

* master_numba_engine.py
* master_sota_engine.py

Problem:

The Numba loader only falls back to the directory if archive-derived problems were not loaded at all, while the SOTA loader merges fallback files more defensively.

Why this matters:

* partial archive degradation can produce a smaller effective corpus in Numba
* cross-engine benchmark sets can silently diverge

Solution advice:

1. Make Numba follow the same merge-and-deduplicate strategy as SOTA.
2. Use tolerant file reading for fallback files.
3. Persist or print a manifest of loaded problem names and sources.

* * *

### 5.6 Medium Severity: Interrupted-run CSV recovery path appears incomplete

Relevant areas:

* master_numba_engine.py
* master_sota_engine.py

Problem:

Both engines define an active-results buffer and flush it during SIGINT handling, but the reviewed files do not appear to populate that buffer during normal execution.

Why this matters:

* interrupted-run CSV export may remain empty or effectively dead
* users may overestimate interruption resilience

Solution advice:

1. Append every completed result row to the active-results buffer immediately after it is produced.
2. Add an interruption integration test.

* * *

### 5.7 High Severity: nb_three_opt should be audited as a likely semantic stub

Relevant area:

* bildiri2026

Problem:

A follow-up audit reported that the public nb_three_opt path delegates to nb_two_opt. If that is the current implementation, the API is semantically misleading.

Why this matters:

* callers do not receive the neighborhood implied by the API name
* any benchmark using the function as a true 3-opt primitive is underpowered silently

Solution advice:

1. Verify the current implementation immediately.
2. Replace it with real 3-opt behavior or explicitly deprecate/rename it.
3. Add a semantic regression test.

* * *

### 5.8 High Severity: MultiLayerLS likely lost iterative convergence behavior

Relevant area:

* ls_engine.py

Problem:

The current layered search structure appears to run as a single pass, while the source adaptation reportedly used repeated improvement until no further gains remained.

Why this matters:

* a single pass is not equivalent to a convergence-seeking local search
* later neighborhoods can unlock new gains for earlier ones

Solution advice:

1. Restore iterative convergence semantics under bounded runtime controls.
2. Add a test where multiple passes improve beyond one pass.
3. Avoid repeating unmeasured claims about exact quality-loss percentage until benchmarked.

### 5.9 Medium Severity: 3-opt and swap appear not to use Numba acceleration in LS engine

Relevant area:

* ls_engine.py

Problem:

2-opt and Or-opt have accelerated paths, but 3-opt and swap appear to remain in pure Python.

Why this matters:

* full-intensity local search does not benefit from Numba consistently
* runtime cost grows more sharply on larger instances

Solution advice:

1. Add dm_np passthrough for 3-opt and swap if kernels already exist.
2. Benchmark before and after the integration.

### 5.10 Medium Severity: Numba cache policy should be reviewed

Relevant area:

* local_search_numba.py

Problem:

A follow-up audit reported that the Numba cache is disabled globally via a dev-null target. If true, that is likely a performance cost rather than a correctness problem.

Why this matters:

* repeated JIT cost can distort short-run runtime perception
* multi-process workloads may lose avoidable warm-cache benefits

Solution advice:

1. Confirm the current cache policy.

2. Prefer per-process temporary cache directories if safe.

3. Document the rationale either way.

The engines rely on the shared utility layer in benchmark_utils.py, which helps reduce duplication across progress logging, metadata, worker selection, problem selection, and timing helpers.

### 6.2 Solver-level SOTA tests are meaningful

The test suite includes checks for:

* valid tours

* destroy and repair edge cases
* resonance behavior
* diversity helper behavior

Relevant files:

* test_sota_e2e.py

The local search stack in ls_engine.py is a reasonable basis for controlled intensification, even though its convergence semantics should now be revisited.

7. UI Improvement Recommendations

---------------------------------

1. Define a strict data contract for the dashboard.

2. Add loaded-file diagnostics and provenance labels.

3. Improve refresh-safe cache behavior.

4. Add convergence-history visualizations once output semantics are cleaned up.

5. Reproduce LaTeX export behavior with missing-optimal rows before promoting NaN handling to a confirmed issue.

----------------------------------------

1. Normalize R2DMA resonance for cyclic tours.

2. Restore iterative convergence semantics in MultiLayerLS.

3. Implement or deprecate misleading nb_three_opt behavior.

4. Extend Numba acceleration to 3-opt and swap if kernels already exist.

5. Improve P-AOEA operator mutation diversity.

6. Revisit Numba cache strategy after correctness issues are fixed.

8. Final Conclusion

--------------------

The academic benchmark codebase is not fundamentally broken. It has a credible architecture, real solver implementations, and useful test coverage. However, several specific issues currently reduce trust in benchmark results and dashboard outputs, especially for resumability, data-model integrity, and solver-semantic faithfulness.

If the identified issues are fixed, the benchmark stack should become substantially more defensible for:

* comparative algorithm studies
* tuning analysis
* publication-quality charts and tables
* reproducible reruns after interruption
