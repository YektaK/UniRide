# Paper-scale run plan: template and approval procedure

Gate D item D-10 (plan `docs/superpowers/plans/2026-10-23-gate-d-analysis-documentation-publication.md`, lines 258-265). Modelled on [`WP_E10_RUN_README_TEMPLATE.md`](WP_E10_RUN_README_TEMPLATE.md). Every paper-scale campaign (Bildiri 2026, YAEM 2026) is run under one filled copy of this template. This template decides no scientific value: run counts, levels and limits are placeholders that name the owner question (OQ-n, DECISION_LOG A18) whose answer fills them. Smoke or pilot runs under no plan produce no superiority, causality or proof claim (AGENTS.md).

Contracts cited below: `manifest.*` = `RunManifestV1` (`uniride-run/v1`, one manifest per run), `index.*` = `RunIndexV2` (`uniride-run-index/v2`, one index per campaign), `study.*` = `StudyManifestV1` (profile `study.json`), `plan.*` = `AnalysisPlanV1` (`analysis_plan.json`). Files of a finished campaign: `run_index.json`, `manifests/<run_id>.json` (each with a detached `.sha256`), the result files, `report.json`/`report.txt` (`academic_benchmark/analysis/manifests.py:48-49`, `academic_benchmark/studies/run.py:410-415`). `python -m academic_benchmark.studies.verify_manifests <dir>` recomputes all checksums (`academic_benchmark/studies/verify_manifests.py:1-30`).

**Run-index completeness (2026-10-26).** `uniride-run-index/v2` records, for every campaign (smoke and paper), the profile and analysis-plan sha256 the run service hashed (`index.profile`, `index.analysis_plan`), the analysis-plan id, the planned runs per cell and in total (`index.planned`), the output folder and the result of the outside-the-repository check made at start (`index.output_location`) and one record per failed run (`index.failed_runs`). This closes gaps G1, G2, G3, G6 and G7 below. The verifier refuses a v1 index (no paper evidence exists under v1; re-run the campaign), compares `index.failed_runs` with the failed-run file, checks `index.planned` against the listed runs, and compares the recorded hashes with the files `index.profile.path` and `index.analysis_plan.path` when the repository is at `index.git.commit` (otherwise it prints a NOTE that the check was not made).

**Citations.** Every `file:line` in this template refers to commit `a75cdde1`, except the evidence lines of the rows of the closed gaps (G1, G2, G3, G6, G7), which refer to the run-index v2 change, and is informative: lines move when the code changes, and the reviewer re-reads the named field in the contract. The consistency test checks the cited contract fields by name, not the line numbers.

## Procedure

1. **Draft.** The lead copies this template into a run-plan file and fills every row of the field table. A value that is not yet decided stays a placeholder and the plan is not offered for approval. The filled plan lives at `docs/run_plans/<study_id>-<YYYY-MM-DD>.md` and is committed, so that its sha256 can be recorded in DECISION_LOG (lead decision 2026-10-24).
2. **Prepare.** The lead merges the owner-approved values in an earlier commit, with `study.status` and `plan.status` still `draft`: `study.algorithm_parameters`, `study.run_count`, `study.scaled_fixed_budget_levels`, `study.secondary_protocol`, `plan.minimum_n_per_cell` set and `plan.unresolved` empty. That commit is, or precedes, the plan's base commit. The approval commit (next section) changes only the two `status` lines. The two file hashes in the plan are the hashes of the two files with exactly that status change applied, computed on a temporary copy and with the same bytes the run service hashes (`academic_benchmark/studies/run.py:205-206`).
3. **Estimate.** The D-04b2 estimate is measured on the machine that will run the campaign and attached (row "Estimate").
4. **Checklist.** Every checklist row below is verified by the lead and the evidence is written into the plan.
5. **Approval** (next section).
6. **Run.** The run service is started in paper mode from a clean checkout of the approved commit, with an output folder outside the repository. It refuses a profile that is not active, an analysis plan that is not active, a dirty or unknown tree and an output folder inside the repository (`academic_benchmark/studies/run.py:440-456`).
7. **After the run.** `verify_manifests <dir> --repository-root <checkout at index.git.commit>` passes and prints a NOTE that the profile and analysis-plan hashes match (a NOTE that the check was not made is not a pass for this item: repeat it in a checkout of that commit); the reviewer reads the "Check after the run" column of every field row against the approved plan and records the result. Any difference makes the campaign not paper evidence (below). A changed profile, analysis plan, commit, environment or seed protocol cannot be resumed; it needs a new plan and a new approval.
8. **Paper report.** The run itself analyses nothing; when a campaign ends, with or without failed runs, it prints the exact command (a campaign with failed runs also gets one line saying that its failed cells are excluded and that the command exits 1 when the report is written, 2 if it is refused), `python -m academic_benchmark.analysis.campaign_report <dir> --paper` (DECISION_LOG A20 L12). Run it on the finished campaign after step 7 passes: it checks the campaign again, reads the profile and analysis plan as committed at `index.git.commit`, analyses every comparison family of the plan (fixed-budget and native separately, never pooled) and writes `paper_report.txt` and `paper_report.json` next to the campaign; the JSON has its own schema name `uniride-paper-report/v1` and the title "UniRide paper report" (the descriptive report keeps `uniride-descriptive-report/v1`; DECISION_LOG A20 L13). It exits 0 when the report is written, 1 when it is written for a campaign that has failed runs (the failed cells are excluded and named), and 2 with the reason when it refuses (smoke or incomplete campaign, a folder that does not verify, a plan that differs from the recorded hash, a dirty tree, a statistics refusal); it is re-runnable and gives the same report from the same campaign.

## Approval

The owner approves the run plan in chat. The lead then records one DECISION_LOG entry (A-series) that names the plan file, its sha256 and the owner's approval, and sets the profile `status: active` (and the analysis plan `status: active`) in the same lead-merged commit as that entry (the approval commit). The plan states its base commit, the commit that already holds the owner-approved values with both statuses still `draft` (step 2). (Lead decision 2026-10-24.) A plan file cannot contain the hash of the commit that contains it, and the profile hash in the plan is the hash of the activated profile, so the manifest commit `index.git.commit` must differ from the base commit only by the approval commit. The reviewer checks it in two steps: `git diff <base commit> <index.git.commit> -- <study.json> <analysis_plan.json>` shows only the two `status` lines (`draft` to `active`), and `git diff --name-status <base commit> <index.git.commit>` lists only those two files, DECISION_LOG and the plan file.

A run whose manifest commit, profile hash or analysis-plan hash differs from the approved plan is not paper evidence. A run with `index.mode` other than `paper`, `index.git.dirty` true, or `index.status` failed without every failure listed in `index.failed_runs` (the verifier compares that list with the failed-run file) is not paper evidence either. Approved plans are never edited in place; a change is a new plan, a new sha256 and a new approval.
