# WP-E6 gap report: the exact references against the GA, week of 2026-10-05

Generated by `scripts/plan_exact_gap_report.py` from committed results only (no solver, no AMPL, no DB). `manifest.json` lists every input file with its sha256, the git commit and dirty flag, the Python and library versions and every output with its sha256. Facts and numbers only; the paper text is written separately.

## Wording rule

- A single snapshot week (service dates 2026-10-05 to 2026-10-09).
- A descriptive gap measurement, not a superiority claim.
- The GA side is one run at seed 42 under the native termination protocol (secondary protocol); the gap is the gap of that run, not of the GA in general. GA labels per row come from the GA source manifests: single_4sw5so: native, seed 42, commit 6be127d, dirty tree True; large+sedan: native, seed 42, commit f29aa3d, dirty tree False; large+doblo_cap3: native, seed 42, commit f29aa3d, dirty tree False.
- Exact rows (waves and options) carry their own protocol `exact_reference_v1` and are never pooled with heuristic rows, with fixed-budget rows or with each other across fleets.
- The day level over the union menu (`union_day_v1`) is the minimum number of cars over the union of the GA and the per-wave exact menus; it is not a global day optimum (EQ3). The day-level value is never `min(GA, union)`: the report shows no such value.
- HiGHS cross-check (EQ4; HiGHS 1.15.1 re-solved every row, Gurobi is the primary solver): single_4sw5so: 228 of 228 optimal rows have the same (K, D) in HiGHS and Gurobi; 0 of 0 proven-infeasible rows are proven infeasible by both; the free-stage optimum is equal in 228 of 228 optimal rows; large+sedan: 837 of 837 optimal rows have the same (K, D) in HiGHS and Gurobi; 167 of 167 proven-infeasible rows are proven infeasible by both; the free-stage optimum is equal in 837 of 837 optimal rows; large+doblo_cap3: 868 of 868 optimal rows have the same (K, D) in HiGHS and Gurobi; 0 of 0 proven-infeasible rows are proven infeasible by both; the free-stage optimum is equal in 868 of 868 optimal rows.

## Columns of `wave_gaps.csv`

`protocol` (always `exact_reference_v1`), `fleet` (`single_4sw5so`, `large+sedan`, `large+doblo_cap3`), `date`, `R`, `option` (`base` or `q`), `option_id` (`base`, `q0`..`q3`), `quota` (empty for `base` and for the single type), `k_kind` (`K` or `K_m`: the route count of the whole wave or of the minimised type), wave columns (`wave_id`, `direction`, `anchor`, `students`, `peak`), `model` (SP), `columns`, `enumeration_labels` (the column and label counts of the enumeration), `ga_option_status`, `comparison` (`compared`, `both_infeasible`, `ga_infeasible_exact_feasible`; for the single type `compared` when K_GA and K* exist), `K_GA`, `K_LB` (+ `K_LB_source`), `K_star`, `D_GA`, `D_LB`, `D_star`, `D_LB_free`, `dK` = `K_GA - K_LB`, `gD` = (D_GA - D_LB) / D_LB when `K_GA = K*` (else empty, `gD_note` `not_comparable_K_GA_gt_Kstar`), `gD_free` = (D_GA - D_LB_free) / D_LB_free, `status` and per stage (`stage1`, `stage2`, `free`) `*_status`, `*_stop_reason`, `*_timing_dependent`, plus `stage2_non_lexicographic` (the design defines it for stage 2 only), `solver`, `solver_version`, `enumeration_seconds`, `solve_seconds`, certificate and cross-check columns (`exact_certified`, `ga_recertified`, `ga_cert_archived`, `ga_cert_agree`, `objective_check`, `exact_le_ga`), the HiGHS columns, the GA labels `ga_protocol`, `ga_seed`, `ga_commit`, `ga_dirty_tree` and `source_result`. Values are copied from the source files as written; no value is invented.

Not available from a source (left empty): single_4sw5so: quota, ga_option_status, note, ga_cert_archived, ga_cert_agree; large+sedan: note; large+doblo_cap3: note (a column empty in every row of a fleet is not recorded by its source, or does not apply there).

## Denominators of the table

`rows` = every source row of (fleet, R, option kind); `compared` = rows with a feasible exact result and a feasible GA result of the same kind (`comparison` = `compared`); `dK_zero_share` = `dK_zero / compared`; `gD_mean` and `gD_max` use only the `gD_comparable` rows (compared rows with `K_GA = K*`); proven-infeasible exact options (`exact_infeasible_proven`), `both_infeasible` and `ga_infeasible_exact_feasible` rows are outside `compared`. Waves (`base`) and options (`q`) are different units and are never summed together; the `q` rows weight the quotas equally.

## Day level (`union_day_v1`)

Labels over the 120 cells: proven_over_union_menu 91, ga_menu_infeasible_for_L 1, both_infeasible_for_L 28, union_not_proven 0, not_independently_confirmed 0, verification_failed 0. Meanings:

Label meanings follow docs/DECISION_LOG.md E07 (cited as DECISION_LOG E07; WP-E4b review, owner decision 2026-10-18 for the two infeasibility labels, lead decisions for the edge cases):

- `proven_over_union_menu`: both CP-SAT runs `optimal` and the TypeScript assignment confirms: minimum cars over the union of the GA and per-wave exact menus; never above the GA-menu result (when both runs are optimal); not a global day optimum (EQ3).
- `both_infeasible_for_L`: the GA-menu run and the union run are both proven infeasible; nothing is compared and no claim is made.
- `ga_menu_infeasible_for_L`: the GA-menu run is proven infeasible and the union run is optimal and confirmed; the union cars are reported as proven over the union menu, with no "never above the GA-menu result" claim and no GA-vs-union difference.
- `both_infeasible_for_L` and `ga_menu_infeasible_for_L` also cover `infeasible_data`, not only `infeasible_for_L`.
- `union_not_proven`: a union run that is still time-limited after the single 60 s re-run (`timing_dependent: true`). `union_not_proven` also covers a time-limited GA-menu run with an optimal union run, because the GA side is then not proven and the GA run is never re-run.
- `verification_failed`: the TypeScript confirmation failed. `verification_failed` also covers the impossible state: the GA-menu run has a selection while the union run is proven infeasible (the union menu contains the GA menu), which is a blocking error.
- `not_independently_confirmed`: the TypeScript confirmation is missing.
- A proven infeasibility is final and is never re-run. Labels occurring in this campaign: only `proven_over_union_menu`, `both_infeasible_for_L` and `ga_menu_infeasible_for_L`; the edge cases above (a time-limited GA-menu run, the impossible state, `infeasible_data`) did not occur (E07).

Replay gate (WP-E4a `replay.csv`): 120 (fleet, date, R, L) cells, request and response differences 0 in all; labels match 91, match_infeasible_for_L 29.

## Figures

x = students per wave, y = `gD`, one panel per R (single type) or per fleet and R (typed fleets); filled circles are rows with `dK = 0`, the only rows with a defined `gD`. Rows with `dK >= 1` (`K_GA > K*`) have no `gD`: they are not drawn, each panel states their count ("dK ≥ 1: n waves (gD undefined, not drawn)") and the y axis is scaled on the drawn `gD` values only (`gD_free` is never plotted on the `gD` axis; it stays in `wave_gaps.csv`). Marker area grows with the number of coincident rows (no count labels); in the typed figure `base` and `q` are offset by 0.14 students so both show. Rows without a GA answer or without an exact result are not drawn and are counted in the panel. Figures are written with matplotlib 3.11.2 (Agg backend, 200 dpi, fixed `svg.hashsalt`, text as paths, no date, creator or software metadata); see `requirements-paper.txt`.

## Notes on the inputs

- The typed `base` rows (`xbase` against the GA `base`) repeat the single-type statistics: the same large type and the same GA base routes (the WP-E10 verifier checked 228 waves against the 4sw5so archive, base routes equal, in `week-2026-10-05-fleet-rerun-large-sedan/README.md` and `...-doblo-cap3/README.md`). The `base` rows of the three fleets are therefore not independent results; the table's `base` rows are identical across fleets.
- WP-E3 `wave_gaps.csv` and WP-E4b `day_gaps.csv` and `day_sums.csv` are not hashed by their own manifests (the WP-E3 and WP-E4a manifests record the sha256 of `exact_routes.json`, the WP-E4b manifest that of the WP-E4a files). WP-E6 pins them: their sha256 is in `manifest.json` under `inputs`.
